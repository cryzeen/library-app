# План проєкту: База даних бібліотеки

## 1. Проблема та мета
Інформація про книжковий фонд бібліотеки часто розпорошена, читачам складно оперативно дізнатися про наявність конкретного примірника та подати заявку на отримання книги. Застосунок забезпечує централізований облік книг, перегляд каталогу з фільтрацією та формування заявок на видачу.

## 2. Користувачі та сценарії
- **Відвідувач/Читач:** перегляд доступного фонду, пошук книги за назвою чи автором, перегляд деталей, подання заявки на бронювання примірника.
- **Бібліотекар:** облік виданих книг, опрацювання заявок, контроль доступності видань у фонді.

### Сценарій 1 (Л 1.1 – збережено)
1. Відвідувач відкриває головну сторінку застосунку.
2. Переглядає опис сервісу та переходить до секції каталогу.
3. Ознайомлюється з переліком книг, їхніми авторами, роком видання та статусом наявності.

### Сценарій 2 (Л 1.2 – додано)
1. Відвідувач переглядає картку книги в каталозі.
2. Переходить за навігаційним посиланням до секції оформлення заявки на бронювання.
3. Бачить попередньо заповнену назву обраної книги та її статус наявності.
4. Ознайомлюється з полями форми (ПІБ читача, мета замовлення) та може очистити введені дані за допомогою кнопки скидання.

### Сценарій 3 (Л 2.1 – додано)
1. Відвідувач відкриває каталог із фільтрацією за назвою/автором та наявністю.
2. Обирає конкретну книгу кліком по кнопці, що передає її стан у спільний Context API та оновлює форму заявки.
3. Заповнює керовану форму читацької заявки (номер квитка, мета, форма видачі) з автоматичним відображенням підсумку.

### Сценарій 4 (Л 2.2 – додано)
1. Відвідувач переходить між окремими сторінками застосунку (`/`, `/books`, `/books/:bookId`, `/loans`, `/loans/new`, `/loans/:requestId/edit`) за допомогою React Router без перезавантаження сторінки.
2. Фільтри каталогу синхронізуються з URL (`?q=...&available=1`), зберігаючи параметр пошуку при копіюванні чи оновленні адреси.
3. При виборі книги або відкритті детальної сторінки адреса дозволяє одразу сформувати заявку `/loans/new?bookId=...`.
4. Перехід на неіснуючу адресу або відсутній ідентифікатор викликає сторінку `NotFoundPage` (404) з посиланнями для повернення до каталогу.

### Сценарій 5 (Л 3.1 – додано)
1. Користувач створює нову заявку через заповнення керованої форми з перевіркою номера квитка, мети замовлення, терміну користування у днях та залежності обов'язкової читальної зали (>14 днів).
2. Після успішної валідації заявка додається до колекції, виводиться системне сповіщення, а користувач перенаправляється на деталі створеного запису (`/loans/:requestId`).
3. Користувач може відредагувати наявну заявку (`/loans/:requestId/edit`) або вилучити її з колекції після підтвердження у діалоговому вікні (`window.confirm`).
4. Список заявок (`/loans`) підтримує текстовий пошук, фільтрацію за форматом видачі та сортування за терміном користування або назвою книги з відображенням параметрів у URL (`?q=...&readingRoom=...&sort=...`).

### Сценарій 6 (Л 3.2 – додано)
1. Доступ до колекції заявок відокремлено від React-компонентів через єдиний асинхронний сервісний контракт (`getAll`, `getById`, `create`, `update`, `delete`).
2. Під час початкового або ручного читання (`reload`) інтерфейс відображає індикатор завантаження (`RequestsGate`), а при збої — причину помилки з можливістю безпечного повтору.
3. У режимі `mock` (`VITE_DATA_SOURCE=mock`) заявки зберігаються у `localStorage` браузера під ключем `library.requests.v1` із керованою затримкою та підтримкою одноразових навчальних відмов; зміни зберігаються після перезавантаження сторінки, а порожній список не перезаписується початковими даними.
4. Під час створення, редагування та видалення інтерфейс блокує повторні дії (`isMutating`), очікує підтвердження сервісу перед оновленням знімка чи навігацією та зберігає чернетку користувача у формі при відмові.
5. Підготовлено адаптер `apiRequestService` на базі `fetch` для подальшого підключення зовнішнього REST API через `VITE_API_BASE_URL` без зміни компонентів інтерфейсу.

## 3. Модель сутностей та збереження
- **Книга (Book):** `id` (string), `title` (string), `author` (string), `genre` (string), `year` (number), `description` (string), `available` (boolean). Довідник книг на поточному етапі залишається локальним (`src/data/books.js`).
- **Читацька заявка (BorrowRequest):**
  - `id` (string): унікальний стабільний ідентифікатор запису;
  - `bookId` (string): посилання на книгу з каталогу;
  - `ticketNumber` (string): номер читацького квитка або ПІБ читача (3–50 символів);
  - `purpose` (string): мета замовлення (10–500 символів);
  - `durationDays` (number): термін користування в днях (1–30);
  - `readingRoomOnly` (boolean): ознака видачі лише в читальний зал (обов'язково `true`, якщо `durationDays > 14`).
- **Модель збереження:** вибір джерела визначається змінною `VITE_DATA_SOURCE`. Автономний режим (`mock`) зберігає колекцію в `localStorage` поточного origin; режим `api` делегує збереження зовнішньому REST-сервісу за адресою `VITE_API_BASE_URL`.

## 4. План сторінок та маршрутів

| Адреса | Компонент | Параметри | Призначення |
|---|---|---|---|
| `/` | `HomePage` | — | Головна сторінка з описом сервісу та посиланнями |
| `/books` | `CatalogContainer` / `BookListPage` | `?q=...&available=1` (пошукові параметри) | Каталог книг із фільтрацією в URL |
| `/books/:bookId` | `BookDetailsPage` | `:bookId` (параметр шляху) | Деталі конкретного видання |
| `/loans` | `BorrowRequestsLayout` / `RequestsPage` | `?q=...&readingRoom=...&sort=...` (пошукові параметри) | Список читацьких заявок із ручним оновленням, пошуком, фільтрацією та сортуванням |
| `/loans/new` | `RequestCreatePage` | `?bookId=...` (пошуковий параметр) | Оформлення нової читацької заявки |
| `/loans/:requestId` | `RequestDetailsPage` | `:requestId` (параметр шляху) | Перегляд збереженої заявки зі знімка колекції |
| `/loans/:requestId/edit` | `RequestEditPage` | `:requestId` (параметр шляху) | Редагування наявної заявки |
| `*` | `NotFoundPage` | — | Повідомлення про невідому адресу (404) |
